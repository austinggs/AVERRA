PURPOSE
Defines server-side gameplay services and their integration with core platform systems.

NORMATIVE LANGUAGE
The terms MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, and MAY are used as engineering requirements.

SERVICES
Game state, machines, inventory, resources, energy, missions, events, achievements, leaderboard, game anti-abuse, analytics bridge, and reward bridge.

TRANSACTION PATTERN
Validate action → lock/compare state → mutate → append game event → publish authoritative response → optionally invoke Reward Engine asynchronously for financial rewards.

CONSISTENCY
Game state uses optimistic versioning or row-level transactions to prevent conflicting updates.

INTEGRATION
Game identities map to Averra users but game resources remain separate from the wallet ledger. Approved game purchases may debit User Funding Balance through a core financial service only after the funding amount is CONFIRMED and available. The game client never mutates funding balance directly and never converts game resources into monetary balances.

SCALABILITY
Use partitionable/player-scoped data, event queues where appropriate, and cache only reproducible/read-optimized data.

IMPLEMENTATION NOTES
This document is a planning/source-of-truth artifact. Concrete library choices, exact endpoint names, provider-specific payload formats, and deployment values may be finalized during implementation only when they preserve the stated invariants and pass the defined verification gates.
